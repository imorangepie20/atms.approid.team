## 체크박스 사용 규칙

- `[ ]`는 미완료이다. 미착수, 진행 중, 일부 구현, 검증 대기 또는 범위 결정 대기도 모두 미체크로 유지한다.
- `[x]`는 해당 작업의 구현과 필요한 검증이 끝났음을 뜻한다. 코드·설정 파일과 검증 명령 또는 결과를 완료 근거에 기록한 뒤 체크한다.
- 템플릿 메뉴나 예시 데이터가 존재하거나 라이브러리를 선택했다는 이유만으로 체크하지 않는다. API·저장·권한이 필요한 업무는 그 흐름까지 검증한다.
- 사전 결정 P, 기능 구현 F, 출시 검증 G는 별도 목록이다. 사전 결정이나 기능 하나의 완료가 모듈 또는 웹·Windows 전체 완료를 뜻하지 않는다.
- 작업 ID는 고정한다. 추가 작업은 해당 그룹의 마지막 번호 다음에 붙이고 기존 ID를 재사용하지 않는다. 범위에서 제외한 작업은 삭제 대신 이유를 기록하고 현황 집계에서 별도 분리한다.
- 조건부 작업은 범위를 먼저 확정한다. 외부 기관 연동, 연결 재무제표, Windows 오프라인 입력은 현재 확정된 구현 범위가 아니다.
- 각 작업 완료 시 체크박스, 아래 현황, 완료 근거와 담당 기능 문서를 함께 갱신한다. 검증이 다시 실패하면 체크를 해제한다. 문서 변경분은 [Hindsight 동기화](HINDSIGHT_SYNC.md)의 30분 예약 실행으로 반영하며 변경마다 즉시 실행하지 않는다.

### 사용자가 코드를 이해할 수 있도록 협업하는 방식

사용자 요청: “내가 네 코드를 완벽히 이해해야해 협조해”.

- 수정 전에 구현 파일 목록과 수정·생성 목적을 제시하고 요청받은 파일은 IDE에서 연다.
- 변경 부분을 찾을 수 있게 주석에 변경 목적과 영역을 표시한다. 코드의 실행 흐름, 설정값의 의미와 변경 이유를 상세히 설명한다.
- 기존 동작, 이번 변경과 미구현 예정 위치를 구분한다. 주석 추가를 기능 구현 완료로 체크하지 않는다.
- 기능 구현 시 요청·응답 또는 입력·출력 예시와 실패 흐름을 함께 설명한다. 새 용어와 라이브러리의 역할을 설명하고 정책 선택을 임의로 가정하지 않는다.
- 변경 후 파일·줄 번호, 변경점과 검증 결과를 제시하여 사용자가 실제 코드를 따라가며 검토할 수 있게 한다.
- 사용자 지시: “테스트는 여러 항목 묶어서 해. 하나 하나 하지말고”. 같은 단계의 관련 변경을 한 작업 단위로 모아 행동 테스트·타입 검사·빌드를 일괄 검증한다. 파일이나 작은 수정마다 테스트를 반복하지 않는다. 독립 검증은 병렬로, 의존 검증은 같은 묶음 안에서 순서대로 실행한다.
- 단계별 검증 묶음을 끝낸 뒤 다음 단계로 진행한다. 실패 수정 후에는 완료 기준에 따라 전체 검증 묶음을 다시 실행한다. 구현 순서 변경은 이유와 변경안을 제시하고 사용자 확정 후 반영한다.
