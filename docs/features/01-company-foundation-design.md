# F01·F08-13 세 번째 묶음: 회사 등록·선택·회계연도 서버 기반

[문서 인덱스](../README.md) · [회사와 사용자 권한](01-company-access.md) · [가입·복구 서버](01-account-lifecycle-design.md) · [구현 계획](../IMPLEMENTATION_PLAN.md)

상태: **세 번째 서버 묶음 구현·검증 완료**. 확정일: 2026-10-05. 확정 근거: 사용자가 이 설계 문서를 지정해 “OK”로 동의했다. 영향 작업 ID: F01-01·F01-02 일부·F01-04·F08-13. 아래 여섯 추천안과 14개 구현 파일, 8개 검증 조건을 확정했다. 첫 전체 검증에서 239개 테스트·8개 조건 모두 PASS를 확인했다. 첫 수정은 공통 설정이며 기존 AUTH/ACC 정책을 보존한다.

## 작업 ID와 선행 조건

대상은 F01-01의 회사 등록·조회·이름 수정·기본 회계연도, F01-04의 회사 목록·선택 계약, F08-13의 해당 감사·원자성이다. 회사 생성자의 초기 관리자 소속은 F01-02의 일부이며 초대·역할 관리 전체 완료로 확대하지 않는다. P-01·02·03·04·10과 F08-10·11·12, 첫 인증 서버와 두 번째 가입/복구 서버의 완료 근거를 재사용한다.

먼저 [AUTH-01·06~10](01-company-access.md#사용자-위임으로-확정한-인증-기본-정책), [회계연도와 규칙 경계 ACC-03·10](07-financial-statements.md#사용자-위임으로-확정한-첫-회계-범위), [회사별 계정 템플릿과 승인된 기초 잔액](04-journals-ledger.md#확정한-계정과목과-기초-잔액)을 따른다. **F01-01~08 또는 F08-13 체크박스를 이 서버 부분만으로 완료하지 않는다.** 같은 F01 단계 안에서 묶음을 나누며 상위 F01 → F13 → 업무 화면 순서를 유지한다.

## 확정한 구현 범위

1. **회사 생성**: 이메일 확인이 끝난 활성 사용자가 회사를 만들고 그 회사의 관리자 소속을 갖는다. 회사·관리자 소속/역할·첫 회계연도·세션 처리·성공 감사를 같은 트랜잭션으로 저장한다. 어느 하나라도 실패하면 회사만 남기거나 역할만 부여하지 않는다.
2. **목록과 선택**: 현재 사용자에게 활성 소속과 조회 권한이 있는 회사만 목록에 포함한다. 선택 요청 때도 현재 회사 소속/역할을 검사하고 회사 정보와 권한 요약을 반환한다. 이후 업무 API는 경로의 회사 ID마다 검증하며 선택했던 회사라는 이유로 다른 요청을 허용하지 않는다.
3. **기본 정보**: 회사 이름과 첫 회계연도 시작/종료일을 입력한다. KRW 및 본인 승인 금지 초기값은 기존 확정값을 사용한다. 지원 기준 K-GAAP과 1월 1일~12월 31일의 제안 입력값은 중앙 설정에서 제공하되 회사의 실제 날짜를 사용자가 명시적으로 보내야 저장한다.
4. **이름 수정**: 현재 회사 관리자만 이름을 수정한다. 읽었던 회사 버전을 보내도록 하여 다른 수정 이후의 오래된 저장 요청은 409로 거부한다. 변경 전/후 이름과 회사·처리자를 감사에 남긴다.
5. **회계연도 조회와 추가**: 등록한 기간은 조회하고 새 기간을 추가할 수 있다. 같은 회사의 기간 중복과 날짜 역전을 거부한다. 기존 기간을 덮어쓰거나 삭제하는 API는 이번 범위에 없다. 기간 정정·적용 기간 변경과 과거 확정본의 연결은 해당 업무 설계에서 이어서 구현한다.
6. **회사 생성에 따른 세션 보호**: 관리자 역할이 새로 생기므로 최근 5분 이내 비밀번호 재확인을 요구한다. 현재 세션은 식별자/CSRF를 교체하고 초기 생성 시각·절대 최대 8시간 만료를 유지한다. 다른 기기의 기존 세션을 폐기해 재로그인하게 한다. 역할 생성과 세션 처리를 같은 트랜잭션에 포함한다.

이번 묶음에서 이름 수정은 회사 설정의 일부이다. 사업자등록번호·주소·세무 담당자, 회사 삭제/휴면, 본인 승인 설정 변경, 초대·세무사 요청·승인·역할/소속 변경·마지막 관리자 보호와 실제 화면 연결은 후속 묶음이다. 회사가 생성되었다는 결과를 장부·신고 준비 완료로 표시하지 않는다. 승인된 계정 템플릿 선택·계정 생성·기초 잔액 확인/승인은 F04·F13을 기다리며 개발 seed 템플릿을 실제 회사에 복사하지 않는다.

## 확정 API 계약

기존 인증 guard·회사 guard·엄격한 입력·고정 오류 응답을 재사용한다. 모든 경로는 인증이 필요하고 GET은 상태를 변경하거나 세션을 연장하지 않는다. POST/PATCH는 Origin·CSRF를 검사한다. 사용자 조작용 회사 생성·선택·이름 수정·기간 추가에만 활동 메타데이터를 선언한다. 응답은 `Cache-Control: no-store`로 처리한다.

| 메서드·경로 | 입력·권한 | 응답·처리 |
| --- | --- | --- |
| GET `/api/companies/options` | 확인된 활성 계정 | KRW·지원 기준·기본 결산월/일·입력 한도. 실제 회사 기간을 자동 확정하지 않음 |
| GET `/api/companies` | cursor·limit, 현재 계정 | 활성 소속과 조회 권한이 있는 회사 목록·다음 cursor. 소속 없는 회사/전역 목록 없음 |
| POST `/api/companies` | creationRequestId·name·startDate·endDate, 활성 계정·5분 재확인 | 회사·관리자 소속·첫 기간·감사 원자 저장. 생성 시 새 쿠키와 세션 복원 형태의 CSRF/만료 정보. 동일 요청 재시도는 기존 회사와 현재 세션 정보 |
| GET `/api/companies/:companyId` | company.read | 회사 ID·이름·KRW·현재 버전·본인 승인 설정의 읽기 값. 내부 생성 요청 해시/다른 사용자 정보 제외 |
| POST `/api/companies/:companyId/select` | 빈 본문, company.read | 선택 가능한 회사 정보와 검증한 현재 역할/권한 요약. 회사 ID를 세션의 전역 선택값으로 저장하지 않음 |
| PATCH `/api/companies/:companyId` | name·version, company.manage | 최신 버전 확인 후 이름 수정과 감사. 실제 변경이 없으면 버전/성공 변경 사건을 추가하지 않음 |
| GET `/api/companies/:companyId/fiscal-years` | cursor·limit, company.read | 해당 회사의 실제 기간 목록·다음 cursor. 날짜는 시간대 없는 YYYY-MM-DD |
| POST `/api/companies/:companyId/fiscal-years` | startDate·endDate·version, company.manage | 현재 회사 버전 확인·기간 추가·버전 증가·감사. 기존 기간 보존 |

회사 생성에는 서버가 사용자 ID와 관리자 역할을 결정한다. 클라이언트가 보낸 creatorId·roles·currency·allowSelfApproval 등의 임의 필드는 거부한다. 생성 요청 ID는 중복 방지용이며 회사 접근 권한이 아니다. 쿠키 원문 식별자는 응답 본문에 넣지 않는다.

회사 목록은 회사 ID 순 cursor, 회계연도는 시작일 순 cursor를 사용한다. cursor의 대상도 현재 사용자/회사 범위에서 확인한다. 소속·역할은 매 요청의 현재 DB 값이며 클라이언트 캐시로 승인하지 않는다. 400 입력, 401 인증/만료, 403 회사/역할/재확인, 409 버전·생성 요청 충돌·기간 중복을 기존 오류 계약에 맞춰 반환한다.

## 저장·동시성·실패 흐름

- **새 업무 모델은 없다.** Company에 `version`과 nullable 생성자 ID·생성 요청 UUID·입력 해시를 추가한다. 생성자/요청 ID의 복합 유일성을 적용한다. 기존 회사는 version=1과 생성 기록 null을 유지하고 데이터의 실제 생성자를 임의로 채우지 않는다. 생성 기록은 세 값 모두 null 또는 모두 존재하도록 제약한다.
- User·CompanyMembership·CompanyMemberRole·FiscalYear·UserSession을 재사용한다. 새 기간의 역전/중복 거부는 기존 DB 제약을 유지하고 승인한 기간 상한을 추가한다. 기존 데이터를 삭제하거나 기존 마이그레이션을 수정하지 않는다. 기존 기간이 새 제약에 맞지 않으면 마이그레이션을 멈추고 해당 상태를 보고한다.
- 회사 생성 트랜잭션은 기존 로그인/복구와 같은 사용자 행 잠금을 사용한다. 잠금 이후 현재 계정·세션·재확인 시각을 다시 검사한다. 중복 요청은 서버가 계산한 생성 입력 해시와 현재 관리자 소속을 재검사하여 기존 회사를 반환하며 권한을 되살리지 않는다.
- 새 생성 요청만 회사→관리자 소속/역할→첫 기간→현재 세션 교체/다른 세션 폐기→회사 생성 감사까지 commit한다. DB/감사/세션 검사 실패는 전체 rollback한다. 쿠키는 commit이 성공한 뒤 전송한다. 첫 응답을 받지 못해 기존 쿠키가 폐기된 경우 로그인 후 같은 요청 ID로 재시도하여 중복 회사를 만들지 않는다. 동시 요청에서 첫 요청이 식별자를 교체했다면 뒤 요청은 트랜잭션의 현재 식별자 검사에서 401이 될 수 있다. 중복 방지를 위해 폐기된 식별자를 재허용하지 않으며 유효한 새 로그인/쿠키로 재시도한다.
- 이름 수정/기간 추가는 회사 행 잠금과 현재 관리자 소속/역할 재검사를 사용한다. guard 이후 권한이 회수된 요청은 트랜잭션에서 거부한다. 예상 version이 현재 값과 다르면 일부 변경 없이 409를 반환한다.
- 현재 세션 교체는 DB에 새 식별자/CSRF 해시만 저장한다. UUID 세션 행의 초기 생성·절대 만료 시각은 유지하고 이미 폐기/만료/교체된 컨텍스트로 다시 교체하지 않는다. 다른 계정의 세션은 영향을 받지 않는다. GET 세션 복원은 기존처럼 읽기 전용이다.
- AuditService와 새 마이그레이션에서 `COMPANY_CREATED`, `COMPANY_RENAMED`, `FISCAL_YEAR_CREATED` 같은 고정 사건을 함께 허용한다. 회사·처리자·요청 ID·시각과 검증한 이름 전/후·기간·버전·초기 역할/폐기 세션 수 등 해당 사건에 필요한 필드만 구성한다. 임의 요청 본문·쿠키·원문 토큰을 감사 입력으로 복사하지 않는다.

계정 템플릿·기초 잔액·전표·세무/회계 규칙·보고서 테이블이나 데이터를 이 묶음에서 만들지 않는다. 회사 기준 표시 K-GAAP은 제품의 지원 범위이고 적용 기간에 승인된 규칙/매핑/서식 선택은 F13의 후속 업무다.

## 사용자에게 설명할 실행 흐름

1. `app.config.ts`의 `COMPANY_CONFIG`가 이름/페이지/기간 한도와 안내 기본값을 제공한다. 실제 회사 날짜를 설정에서 자동 확정하지 않는다. `companies.schemas.ts`는 strictObject로 과다 필드를 거부하고 이름을 앞뒤 정리하며 UUID 대소문자를 정규화한다. Date 왕복 비교로 2월 30일 같은 자동 날짜 보정을 거부한다.
2. `companies.controller.ts`의 8개 경로에 기존 인증/권한 guard와 입력 파이프를 연결했다. 회사 생성은 Origin/CSRF/5분 재확인과 활동 선언을 통과한 뒤 service에 간다. 조회는 활동을 선언하지 않는다.
3. `companies.service.ts`는 User → 현재 세션 → 회사 → 소속/역할 순으로 필요한 행을 잠근다. 잠금은 동시 요청이 같은 자료를 덮어쓰지 않도록 DB에서 처리 순서를 정하는 방식이다. 쓰기 직전 계정/토큰/만료와 현재 역할을 다시 검사한다. 예전 guard 결과만으로 저장하지 않는다.
4. 생성은 요청 UUID와 정규화된 이름/날짜의 SHA-256 해시로 재시도를 구분한다. 새 요청이면 회사/관리자/첫 기간/세션/감사를 같은 DB 트랜잭션에 쓴다. 같은 요청이면 현재 관리자 권한이 남아 있는지 확인하고 기존 결과를 반환한다. 오래된 쿠키로 재시도하면 401이며 로그인·재확인 후 같은 요청 ID를 재사용한다.
5. `session.service.ts`는 현재 세션 UUID/생성/절대 만료를 유지하면서 원문 식별자와 CSRF를 바꾸고 해시만 저장한다. 다른 기기의 같은 사용자 세션을 폐기한다. `companies.controller.ts`는 commit 후 새 쿠키를 HttpOnly로 전달한다. JSON에는 최소 사용자·CSRF·만료만 포함한다.
6. 이름/기간 수정은 읽은 `version`과 DB 버전이 같아야 한다. 실제 변경일 때 버전을 1 증가하고 검증한 변경값만 감사에 기록한다. 이름이 같으면 버전/변경 감사를 추가하지 않는다. 같은 회사 기간은 양끝을 포함해 겹치지 않아야 한다. 기존 기간 수정/삭제 경로는 없다.
7. `audit.service.ts`는 고정 사건 종류와 허용 변경 필드만 구성한다. 성공 감사 저장이 실패하면 회사/역할/기간/세션 변경도 모두 rollback한다. guard의 활동 시간 갱신은 기존 계약대로 별도 처리이므로 실패 시에도 유효한 조작 요청의 활동 시각은 남을 수 있다. 회사 성공 감사나 업무 부분 저장을 남기는 것과 구분한다.

요청 예시: `POST /api/companies`에 `{ "creationRequestId": "a0000000-0000-4000-8000-000000000001", "name": "예시 회사", "startDate": "2026-01-01", "endDate": "2026-12-31" }`를 보낸다. 유효한 로그인 쿠키·CSRF·Origin·재확인이 필요하다. 결과는 `{ company, created, session }`이고 쿠키 원문은 JSON에 없다. 이후 `PATCH /api/companies/{companyId}`에는 `{ "name": "수정 회사", "version": 1 }`을 보내며 다른 수정이 먼저 끝나면 409를 받는다.

Hindsight는 사용자 지시대로 PT30M 예약 실행을 유지한다. 새 문서 원격 일치는 이번 검증에 포함하지 않았다. 확인한 마지막 실행 기록(2026-10-05 03:05 UTC)은 동기화 exit 0 이후 `--check` exit 1이며 `docs/features/01-account-lifecycle-design.md`의 원격 내용/검색 메모리 불일치를 보고했다. 이 과거 기록으로 이번 변경이 동기화됐다고 보고하지 않으며 저장소 원문을 우선 사용한다.

[구성원 조회·역할 변경·소속 중지 서버](01-company-members-design.md)를 다음 범위로 정리했다. 마지막 관리자·권한 회수 기반부터 갖춘 뒤 초대/접근 요청을 연결하는 분할 순서와 대상 세션 처리는 2026-10-05 사용자가 구성원 설계를 지정해 “OK”로 동의했다. 11개 파일을 구현했고 전체 284개 테스트·8개 완료 조건이 PASS여서 네 번째 서버 부분도 완료 기록했다. 완료된 회사 서비스에 대한 “OK”를 새 범위 승인으로 확대하지 않는다. 이 문서의 회사 서버 완료 기록·8개 체크는 보존한다.
