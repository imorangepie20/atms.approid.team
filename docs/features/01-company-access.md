# 회사와 사용자 권한 개발 문서

[문서 인덱스](../README.md) · [전체 개요](../PROJECT_DECISIONS.md) · [개발 순서와 미정 사항](../ROADMAP.md)

문서 ID: F01

상태: P-01 SaaS 및 P-02 정책 확정. 첫 인증·세션/권한·두 번째 가입/복구·세 번째 회사 등록/선택/이름/기간·네 번째 구성원 조회/역할 변경/소속 중지·다섯 번째 초대/접근 요청·여섯 번째 본인 승인 설정 서버 부분은 구현·검증 완료했다. 회사·구성원·관리자 초대/접근 요청·초대 수락/본인 요청·본인 승인 설정·가입/확인/복구 브라우저 부분도 완료했다. 로그인 중 비밀번호 변경/전체 기기 로그아웃 화면·재활성화·운영 이메일 전달은 후속이다. 부분 검증은 전체 기능 완료와 구분한다.

자기 계정 보안 화면 부분 완료(2026-10-06): 사용자 “확정”으로 [Settings 계정 보안 패널](01-account-security-browser-design.md)의 B1~B7·파일12·검증8을 승인했다. 첫 미통과7개로 중단한 뒤 사용자 “다음”으로 같은 범위의 원인 수리를 재개했다. F01-03·06·08/F08-09·14·15의 부분은 최종8조건PASS·build/lint exit0·Appearance16·E2E156·API413/19파일, 실제 변경/전체 종료·각각2세션 폐기·다른 사용자/비밀번호/소속/역할 보존·감사3/변경 알림·기본20테이블 동일·UI/API200을 확인했다. 첫 실패64파일·서버/DB/AUTH 정책·상위 체크·직전 완료를 유지하며 재활성화·MFA·기기 목록·운영 전달은 후속이다.

이 문서의 상세 기능, 데이터와 완료 기준은 현재 요구사항을 개발 단위로 풀어쓴 설계안이다. 구현 후 검증 기준은 아직 실행 결과가 아니다. 사용자 확정사항과 기존 적용 기록은 별도로 표시한다.

본인 승인 설정 브라우저 부분 완료(2026-10-06): 사용자 “확정”으로 [설정 화면 설계](01-company-settings-browser-design.md)의 S1~S6·파일 항목10·검증 조건8을 구현했다. 기존 관리자/5분 재확인/shared version/no-op·감사·세션 보존 정책으로 `/companies`의 명시적 설정 변경·확인/충돌·미확인 결과 조회를 연결했다. 영향 ID: F01-01·05·06·08/F08-09·14·15의 설정 화면 부분. 최종 8조건 PASS·Appearance16·E2E82·API413·실제 양방향 설정/version/감사2·역할/현재/다른 기기 세션·CSRF/절대 만료·다른 회사·기본atms20테이블 보존을 확인했다. 실제 전표 승인과 상위 전체 체크는 후속으로 유지한다.

공개 계정 화면 부분 완료(2026-10-06): 사용자 “확정”으로 [가입·이메일 확인·복구 브라우저 설계](01-account-lifecycle-browser-design.md)의 A1~A7·파일15·기존 공개API5·검증 조건8을 승인했다. F01-02·03·06·08/F08-09·14·15의 공개 계정 화면 부분이다. 첫 중단 후 사용자 “다음”으로 같은 문서/완료 후 메일 재진입을 감지하는 토큰 수명을 수정하고 전체 검증을 반복했다. 최종8조건·build/lint·Appearance16·E2E116·API413·실제 메일 확인/복구/로그인·대상 세션2폐기/다른 사용자/현재 쿠키·감사3·기본atms20테이블 전후 보존이 PASS다. 실패 기록과 기존 AUTH 정책/가입만으로 세션·회사 소속을 만들지 않는 계약을 보존한다. 로그인 중 비밀번호 변경·전체 기기 로그아웃·운영 SMTP와 전체 기능 완료는 후속으로 구분한다.

## 목적과 범위

회사별 업무 데이터와 사용자의 접근 범위를 관리한다.

- 회사와 사용자 등록, 회사 소속 및 역할 관리
- 로그인, 회사 선택과 접근 권한 검증

## 입력과 결과

| 구분 | 내용 |
| --- | --- |
| 입력 | 회사 정보, 사용자, 소속, 역할과 요청한 작업 |
| 결과 | 선택 가능한 회사, 사용자 세션과 작업별 허용 또는 거부 결과 |

회사 등록·기본 회계 설정(F01-01)은 [P-03 첫 회계 범위](07-financial-statements.md#사용자-위임으로-확정한-첫-회계-범위)를 따른다. 사용자 위임으로 확정한 회계연도 기본값과 회사별 실제 기간을 구분하고, 적용 기간·변경 이력을 회사 업무 데이터로 관리한다. 회사 등록/이름/기간의 서버 부분은 [회사 기반 설계와 실행 기록](01-company-foundation-design.md)에서 구현·검증했다. 기간 정정/이력·적용 규칙·실제 화면은 후속이다.

회사별 세무 담당과 신고자료 검토·최종 확인은 사용자 위임으로 확정한 [P-04 첫 세무 범위](06-tax.md#사용자-위임으로-확정한-첫-세무-범위)를 따른다. 전문성을 확인한 지정 세무 검토자의 검토 의견과 회사 관리자의 자료 최종 확인을 구분한다. 외부 세무사 역할의 기존 전표 승인·회사 관리 제한은 유지하며 이 추가 세무 작업의 권한 검사는 F01·F06·F08-13에서 구현한다. 회사 관리자는 서비스 전체 규칙 승인 권한을 얻지 않는다.

## 확정한 운영 모델

**P-01: SaaS.** 외부 고객사가 가입해 각자 회사의 자료를 관리한다. 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

회사별 접근 범위는 아래 처리 규칙을 따른다. 실제 회사·사용자 모델과 접근 제어는 F01 및 F08-11·13에서 구현한다.

## 확정한 로그인 방식

**P-02 중 로그인 방식: 이메일 + 비밀번호.** 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다. 첫 서버 로그인 API는 [인증·세션 설계](01-auth-session-design.md)의 확정 범위에서 구현·검증했다.

5개 역할과 세션·가입·복구 정책은 확정했다. 사용자가 남은 P-02 정책 선택을 일반적인 방식으로 위임했으며 아래 기본 정책을 채택했다. 첫/두 번째 서버 묶음의 실제 인증·가입·복구·세션·접근 검사 API/DB 계약은 구현·검증했으며 회사 관리·초대·역할 변경·웹 화면은 후속이다.

### 사용자 위임으로 확정한 인증 기본 정책

확정일: 2026-10-05. 사용자 지시: “이 부분은 일반적으로 사용하는 방식으로 정하고 넘어가자”. 기존에 직접 선택한 정책은 유지하고, 남은 P-02 정책은 에이전트가 보안 지침과 프로젝트의 SaaS 운영 모델을 바탕으로 선정했다. 아래 값은 **사용자 위임에 따른 프로젝트 결정**이며 각 수치를 보편적인 의무 표준으로 주장하지 않는다. 영향 작업은 F01-01~08, F08-10·11·13이며 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

| 항목 | 확정한 정책 |
| --- | --- |
| AUTH-01 가입·회사 소속 | 이메일 + 비밀번호로 직접 가입하고 이메일 확인 후 업무 접근을 허용한다. 새 회사를 만든 사용자는 그 회사의 관리자이다. 가입만으로 기존 회사 접근 권한은 부여하지 않는다. 기존 회사는 초대 수락 또는 승인된 접근 요청으로 소속을 부여한다. |
| AUTH-02 비밀번호 | 첫 웹 버전은 이메일 + 비밀번호 인증이며 MFA·소셜 로그인은 후속 확장 범위이다. 비밀번호는 15~128자이며 Unicode와 공백을 허용하고 앞뒤 공백을 임의로 제거하지 않는다. 대소문자·숫자·특수문자 조합이나 정기 변경을 강제하지 않는다. 흔하거나 유출된 비밀번호를 차단하고, 유출 확인 시 변경한다. |
| AUTH-03 비밀번호 저장 | 사용자별 salt를 포함한 Argon2id 해시를 사용한다. 초기 최소 설정은 메모리 19 MiB, 반복 2, 병렬도 1이다. 비밀번호 원문은 저장하거나 로그에 남기지 않으며, 구현 단계에서 실제 홈서버 부하를 측정한다. |
| AUTH-04 이메일 확인·계정 복구 | 이메일 확인 링크는 24시간, 비밀번호 재설정 링크는 30분 만료의 일회용 토큰이다. 토큰은 안전한 난수로 발급하고 서버에는 해시만 저장한다. 재발송하면 이전 미사용 토큰을 무효화한다. 복구 응답으로 계정 존재 여부를 드러내지 않는다. 비밀번호 변경·복구 완료 시 모든 기존 세션을 무효화하고 재로그인하게 한다. 복구 완료 알림을 발송한다. |
| AUTH-05 로그인·발송 제한 | 계정별 15분 내 로그인 실패 5회 시 15분 대기, IP별 로그인 요청은 15분당 30회로 제한한다. 이메일 확인·복구 발송은 계정별 15분당 3회 및 IP별 15분당 20회로 제한한다. 영구 잠금 대신 제한 시간이 지나면 재시도할 수 있다. 오류는 계정 존재·비밀번호 오류·사용 중지 여부를 구별해 노출하지 않는다. |
| AUTH-06 활동·최대 세션 시간 | 기존 1시간 미사용 만료와 활동 시 연장을 유지한다. 사용자 조작에 따른 인증된 업무 조회·입력·저장 요청을 활동으로 인정한다. 자동 새로고침·폴링·백그라운드 요청·health 확인은 연장하지 않는다. 로그인 후 절대 최대 유지 시간은 8시간이며 활동해도 이 한도를 연장하지 않는다. 만료 판단은 서버에서 수행한다. |
| AUTH-07 세션 식별자·민감 작업 | 로그인 성공과 권한 변경 시 영향을 받는 세션의 식별자를 재발급하며 기존 식별자는 폐기한다. 새 식별자를 발급해도 절대 최대 유지 시간의 시작점은 초기화하지 않는다. 비밀번호·이메일·역할·본인 승인 설정 변경 및 마감 취소는 최근 5분 이내 비밀번호 재확인을 요구한다. 정기 식별자 교체 타이머는 첫 버전에 추가하지 않는다. |
| AUTH-08 웹 쿠키·CSRF | 운영은 동일 출처 HTTPS에서 HttpOnly·Secure·SameSite=Strict, Path=/, Domain 미지정의 세션 쿠키를 사용한다. 상태를 변경하는 요청은 서버 세션에 연결된 CSRF 토큰과 Origin 검사를 적용하고 GET으로 상태를 변경하지 않는다. 브라우저 localStorage에 세션 식별자를 저장하지 않는다. 로컬 HTTP 개발에서만 Secure 비활성화와 별도 개발 쿠키 이름을 허용하며 운영 설정에서는 거부한다. |
| AUTH-09 초대·접근 요청 | 초대와 세무사 접근 요청은 7일 만료이다. 초대는 지정 이메일을 확인한 사용자가 수락해야 효력이 생긴다. 관리자는 미수락 초대를 취소·재발송할 수 있고, 재발송하면 이전 링크는 무효화된다. 회사·대상별 대기 초대 또는 접근 요청은 각각 1개만 유지하며 반복 제출로 중복 소속·권한을 만들지 않는다. 요청자는 대기 요청을 취소하고 관리자는 승인·반려할 수 있다. 만료·취소·반려 후에는 새로 제출할 수 있다. 처리 시점에도 관리자 권한과 요청자 계정 상태를 다시 확인한다. |
| AUTH-10 회사 관리·감사 | 역할 부여·회수와 회사 소속 중지는 회사 관리자가 처리하며 해당 회사에만 적용한다. 마지막 활성 회사 관리자를 제거하는 작업은 거부한다. 초대·요청·소속·역할·본인 승인 설정 변경에는 처리자·회사·시각·변경 내용을 기록한다. 로그에 비밀번호·세션 식별자·복구 토큰 원문을 기록하지 않는다. 본인 승인 설정은 승인 실행 시점의 현재 값을 적용하며 설정 변경 자체가 승인 권한을 부여하지 않는다. |

로그인 시간, 링크 만료, 시도 제한, 해시 비용 등의 설정값은 [공통 설정 파일 관리](08-platform.md#확정한-설정값-관리-원칙)에서 한 번 정의한다. 서비스 비밀값은 기존 환경 변수에서 주입하고 설정 파일이 참조한다. 공통 설정 파일과 첫 인증 서버 코드는 구현·검증했으며 [실제 범위·파일 목록](01-auth-session-design.md)을 따른다. [두 번째 서버 묶음](01-account-lifecycle-design.md)에서 SMTP 연동과 로컬 캡처 흐름을 구현·검증했으며 운영 실제 전달은 별도다. 이메일 발송 제공자, 라이브러리와 요청·응답 스키마는 구현 단계의 기술 선택이다. Windows의 세션 보관·복원은 P-08·F11-03 설계에서 다룬다.

기술 근거는 [OWASP 인증](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [비밀번호 저장](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [비밀번호 복구](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)를 참조한다. 8시간 최대 유지와 24시간·30분·7일 링크 만료, 시도 제한 횟수는 이 프로젝트에서 선택한 기본값이다.

## 확정한 웹 세션 방식

**P-02 중 웹 로그인 세션: 서버 세션 방식 + PostgreSQL 저장소.** 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

- 로그인 세션 상태를 PostgreSQL에 저장하고 서버에서 유효성을 확인한다.
- 브라우저는 HttpOnly·Secure·SameSite 쿠키로 세션 식별자를 전달한다. 회사·역할 권한을 쿠키 내용만으로 신뢰하지 않는다.
- 보호된 API 요청마다 세션 유효성과 사용 중지 여부, 현재 회사 소속·역할 권한을 확인한다. 회사 권한 회수 후 해당 회사의 보호된 요청을 거부한다.
- 로그아웃 시 서버의 세션을 무효화한다. 브라우저 쿠키 삭제만으로 로그아웃 처리를 끝내지 않는다.

로그인 유지·만료 시간값과 활동 시 연장, 동시 로그인·로그아웃은 아래 확정사항을 따른다. 식별자 재발급·쿠키·CSRF·개발 환경 예외는 위 AUTH-06~08을 적용한다. 세션 테이블과 첫 서버 인증·세션 코드는 구현·검증했다. 가입·이메일·복구 서버는 [두 번째 범위](01-account-lifecycle-design.md)에서 구현·검증했다. 회사 관리·초대·역할 변경·화면 연결은 후속이다.

보호된 쿠키와 서버 측 세션 무효화의 기술적 근거는 [OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)을 참조한다.

### 확정한 로그인 시간값과 설정 관리

**로그인 유지·만료 시간값: 1시간(60분, 3,600초).** 사용자 지시: “로그인 유지만료 시간 같은 설정값은 설정파일 하나에 모아서 처리하도록하자. 한시간으로해”. 확정일은 2026-10-05이며 확정 근거와 영향 작업은 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

로그인 시간 등 변경 가능한 설정값은 [공통 설정값 관리 원칙](08-platform.md#확정한-설정값-관리-원칙)에 따라 하나의 설정 파일에서 관리한다. 세션 검증과 쿠키 등 이 시간값을 사용하는 곳에 각각 숫자를 복사하지 않는다.

**만료 기준: 마지막 활동 후 1시간 미사용 시 만료하며, 활동할 때마다 만료 시각을 연장한다.** 사용자 확정 근거: “연장되는 방식”(2026-10-05). 마지막 활동이 09:40이면 만료 시각은 10:40이며, 그 전에 다시 활동하면 새 활동 시각부터 60분으로 갱신한다. 60분 동안 활동이 없어 만료된 세션은 이후 요청으로 되살리지 않고 다시 로그인해야 한다.

1시간은 미사용 만료에 적용한다. 사용자 위임으로 별도 확정한 최대 유지 8시간과 활동 판정은 AUTH-06을 따른다. 시간 연장과 세션 식별자 교체는 다른 동작이며 재발급은 AUTH-07을 따른다. 실제 설정 파일과 첫 서버 세션 기능은 [확정 범위](01-auth-session-design.md)에서 구현·검증했다. 웹 화면의 실제 연결은 후속 묶음이다.

### 확정한 동시 로그인과 로그아웃

**여러 기기 동시 로그인을 허용하고, 현재 세션 로그아웃과 모든 기기 로그아웃을 제공한다.** 확정일: 2026-10-05. 사용자 확정 근거: 여러 기기 동시 로그인·세션별 1시간 미사용 만료·개별 및 전체 로그아웃을 제시한 1번을 사용자가 “1”로 선택했다. 영향 작업은 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

- 다른 기기나 브라우저에서 새로 로그인해도 기존 세션을 종료하지 않는다.
- 각 세션에 마지막 활동 후 1시간(60분) 미사용 만료와 활동 시 연장을 독립적으로 적용한다. 한 세션의 활동으로 다른 세션의 만료 시각을 연장하지 않는다.
- 현재 세션 로그아웃은 요청한 세션만 서버에서 무효화한다. 다른 세션은 각각의 만료·무효화 정책에 따라 유지된다.
- 모든 기기 로그아웃은 해당 사용자 계정의 현재 세션을 포함한 모든 기존 세션을 서버에서 무효화한다. 다른 사용자 계정의 세션에는 영향을 주지 않는다. 이후 보호된 요청은 다시 로그인하기 전까지 거부한다.

이 정책은 F01-03·08 및 F08-11·13에서 구현·검증하며 F11-03의 Windows 인증 연계에서도 참조한다. Windows 앱의 세션 보관·복원 계약은 후속 설계 대상이다. 서버의 동시 로그인과 현재/전체 로그아웃은 첫 묶음에서 검증했으며 웹 화면 연결은 후속 묶음이다.

## 확정한 역할 구성

**P-02 중 역할 구성: 총 5개.** 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

- 회사 관리자
- 회계 담당자
- 승인자
- 조회 전용
- 외부 세무사

역할 목록과 외부 세무사 기본 권한·회사별 접근 및 관리자 회수는 확정했다. 추가 작업 권한은 [마감·정정 권한](05-approval-closing.md#확정한-마감과-정정-권한)을, 초대·요청 세부 정책은 AUTH-09~10을 따른다. 역할·권한 기능은 구현 전이다.

## 확정한 역할 겸임

**P-02 중 역할 겸임: 같은 회사에서 한 사용자에게 여러 역할을 부여할 수 있다.** 예를 들어 회사 관리자와 회계 담당자를 겸임할 수 있다. 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

역할을 겸임해도 아래 본인 승인 정책은 그대로 적용한다. 기본 설정에서는 작성자와 승인자 역할을 함께 가진 사용자도 자신이 작성한 전표를 승인할 수 없다. 이번 선택은 다른 회사의 소속·권한을 자동으로 부여하지 않는다. 역할의 허용 권한은 아래 합산 규칙과 확정한 마감·정정 권한을 따른다. 실제 기능은 구현 전이다.

### 확정한 권한 합산과 공통 제한

**같은 회사에서 부여받은 역할의 허용 권한을 합산하고, 공통 제한을 우선 적용한다.** 확정일: 2026-10-05. 사용자 확정 근거: 역할의 허용 권한 합산·공통 제한 우선·미부여 작업 거부를 제시한 1번을 사용자가 “1”로 선택했다. 영향 작업은 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

- 요청한 회사에서 현재 부여받은 역할의 허용 권한을 합친다. 다른 회사의 역할이나 권한을 가져와 합산하지 않는다.
- 유효한 세션, 사용 가능한 계정, 현재 회사 소속·접근 범위를 먼저 확인한다. 본인 승인 정책과 해당 업무에서 확정한 상태별 제한도 함께 적용한다. 공통 제한에 걸린 작업은 역할의 허용 권한이 있어도 거부한다.
- 공통 제한을 충족한 뒤 현재 역할 중 하나 이상이 해당 작업을 허용할 때만 승인한다. 어느 역할에서도 허용하지 않은 작업은 거부한다.
- 역할에 권한이 없는 것은 다른 역할의 허용 권한을 취소하는 명시적 거부가 아니다. 조회 전용 역할은 다른 역할의 허용 권한을 취소하지 않는다.
- 역할별 명시적 거부 권한을 별도로 설정하는 2번은 이번 범위에 포함하지 않는다. 본인 승인 허용 설정도 승인 역할의 권한을 자동으로 부여하지 않는다.

| 겸임 사례 | 공통 제한을 충족했을 때의 결과 |
| --- | --- |
| 조회 전용 + 회계 담당자 | 회계 담당자의 증빙 등록·전표 초안 작성·수정·승인 요청 가능 |
| 회계 담당자 + 승인자 | 두 역할의 허용 권한을 합산하되, 기본 본인 승인 금지 설정에서는 자신이 작성한 전표 승인 불가 |
| 회사 관리자의 권한 + 회사 소속 해제 | 해당 회사의 보호된 요청 거부 |

F01-05·06·07·08 및 F08-13의 서버 권한 검사와 화면 표시에서 이 규칙을 참조한다. 마감·정정의 역할별 권한은 후속 사용자 위임으로 아래 연결 문서에서 확정했다. 상태 전이·정정 가능 기간은 F05 업무 설계에서 다루며 권한 기능은 구현 전이다.

## 확정한 외부 세무사 기본 권한

**P-02 중 외부 세무사 기본 권한: 자료 조회·보고서 다운로드 + 증빙 등록 + 전표 초안 작성·수정.** 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

- 자료 조회와 보고서 다운로드
- 증빙 등록
- 전표 초안 작성·수정

전표 승인과 회사 관리 권한은 외부 세무사 역할 자체에 포함하지 않는다. 역할 겸임은 이미 허용했으므로 별도 역할로 부여할 권한은 해당 역할 정책을 따른다. 이 기본 권한 선택으로 확정 전표의 수정이나 증빙 수정·삭제를 확정하지 않는다. 회사별 접근·초대·권한 회수 정책은 아래 확정한 회사 접근 절을 따른다. 실제 권한 기능은 구현 전이다.

## 확정한 회사 관리자 기본 권한

**P-02 중 회사 관리자 기본 권한: 관리 권한 + 회계 담당자·승인자 권한 기본 포함.** 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

- 회사 설정·사용자 초대·역할 관리·본인 승인 설정 변경
- 회계 담당자·승인자 권한을 기본 포함하며 두 역할을 별도로 부여해야 하는 조건을 두지 않음

회사 관리자는 해당 회사 범위에서 위 권한을 갖는다. 기본 상태에서는 관리자도 자신이 작성한 전표를 승인할 수 없으며 회사가 본인 승인을 허용한 경우에만 본인 승인 정책에 따라 승인할 수 있다. 관리자 권한이 다른 회사의 접근 권한을 자동으로 부여하지 않는다.

회계 담당자·승인자의 아래 기본 권한표는 회사 관리자에게도 적용한다. 추가 작업 권한은 확정한 마감·정정 권한을 따른다. 관리자도 확정 전표 수정·마감·정정 등 상태별 제한을 지킨다. 실제 권한 기능은 구현 전이다.

## 확정한 기본 권한표

**P-02 중 회계 담당자·승인자·조회 전용 기본 권한을 확정했다.** 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

공통 권한은 자료 조회·보고서 다운로드이며 모두 소속·권한이 있는 회사 범위에 적용한다.

| 역할 | 확정한 기본 권한 |
| --- | --- |
| 회계 담당자 | 공통 + 증빙 등록·전표 초안 작성·수정·승인 요청 |
| 승인자 | 공통 + 전표 승인·반려·확정 |
| 조회 전용 | 공통만 |

회사 관리자는 위 회계 담당자·승인자 권한을 기본 포함한다. 조회 전용 역할 자체에는 입력·승인 권한을 부여하지 않으며, 다른 역할을 겸임하는 경우에는 해당 역할의 권한을 따르되 회사 범위와 본인 승인 정책을 지킨다. 추가 작업 권한은 사용자 위임으로 확정한 [마감·정정 권한](05-approval-closing.md#확정한-마감과-정정-권한)을 따른다. 실제 권한 기능은 구현 전이다.

## 확정한 외부 세무사 회사 접근

**P-02 중 외부 세무사 회사 접근: 관리자 초대 + 세무사 접근 요청 후 회사 관리자 승인.** 확정일과 사용자 선택 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

- 회사 관리자가 외부 세무사를 초대하는 흐름과 세무사가 신청해 회사 관리자가 승인하는 흐름을 모두 지원한다.
- 접근 요청을 제출한 것만으로는 회사 자료를 볼 수 없다. 승인 시 해당 회사에 외부 세무사 역할과 확정한 기본 권한을 연결한다.
- 접근 권한은 회사별로 부여한다. 다른 회사의 접근 권한은 자동으로 생기지 않는다.
- 해당 회사 관리자가 권한을 회수할 수 있으며, 회수 후 해당 회사 자료의 보호된 요청은 거부한다.

초대·요청의 만료·취소·중복 처리는 AUTH-09~10으로 확정했다. 상세 화면·입력·응답 스키마는 구현 단계에서 설계하며 실제 기능은 구현 전이다.

## 제외한 세무사 직접 접근 요청

**이전 결정 기록이며 현재 개발 범위는 접근 요청 포함이다.** 최초 제외 지시는 이후 사용자의 2번 선택과 “이번걸로 해” 지시로 대체됐다. 확정일과 사용자 지시 근거는 [사전 결정 확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 따른다.

현재 적용할 회사 접근 정책은 위 확정한 외부 세무사 회사 접근 절을 따른다. 이 절은 결정 변경 이력을 찾기 위한 참조이며 기능 제외 지시가 아니다.

## 확정한 작성자·승인자 분리

**P-02 중 전표 본인 승인: 회사별 설정, 기본값은 본인 승인 금지.** 승인 권한이 있어도 기본 상태에서는 다른 사용자가 승인한다. 회사가 본인 승인을 허용한 경우에만 승인 권한이 있는 작성자가 자신의 전표를 승인할 수 있다. 상세 정책과 미정 사항은 [승인과 마감 및 정정](05-approval-closing.md#확정한-본인-승인-정책)을 참조한다.

## 데이터와 처리 규칙

- 회사 식별자, 사용자 식별자, 소속과 역할을 업무 데이터에 연결한다.
- 조회·변경·파일 다운로드·보고서 출력에서 동일한 회사 범위를 적용한다.
- P-02의 로그인·가입·복구·세션·초대·역할·권한 정책은 확정했다. 코드·DB·실제 동작 검증은 F01 및 F08의 구현 작업으로 별도 관리한다.

## 구현 후 검증 기준

- [ ] 다른 회사의 전표·증빙·보고서 식별자를 요청하면 접근이 거부된다.
- [ ] 역할별 허용·금지 작업을 서버 API와 화면에서 일관되게 검증한다.
- [ ] 외부 세무사 역할만 가진 사용자는 자료 조회·보고서 다운로드·증빙 등록·전표 초안 작성·수정이 가능하고, 전표 승인·회사 관리 권한은 갖지 않는다.
- [ ] 회사 관리자는 관리 권한과 회계 담당자·승인자 권한을 기본 포함하지만 본인 승인 정책과 회사 범위·상태별 제한을 지킨다.
- [ ] 같은 회사에서 여러 역할을 부여·회수할 수 있고, 겸임하더라도 본인 승인 정책과 다른 회사의 접근 범위를 지킨다.
- [ ] 관리자 초대와 접근 요청·승인 흐름을 모두 검증하며, 승인 전 접근과 다른 회사의 접근을 차단하고 관리자 권한 회수 후 보호된 요청을 거부한다.
- [ ] 로그아웃 또는 소속 해제 이후 보호된 요청의 결과를 검증한다.
- [ ] PostgreSQL 세션 저장·쿠키 전달·요청별 현재 권한 검사를 검증하고, 로그아웃으로 서버 세션을 무효화한 뒤 보호된 요청을 거부한다.
- [ ] 새 로그인 이후 기존 세션을 유지하고, 세션별 1시간 미사용 만료·활동 시 연장을 독립적으로 적용한다.
- [ ] 현재 세션 로그아웃은 해당 세션만, 모든 기기 로그아웃은 해당 계정의 모든 기존 세션을 무효화하며 다른 계정의 세션을 유지한다.

## 후속 구현 설계

- 이메일 발송 제공자·인증 라이브러리, 상세 화면·API·DB 계약과 실제 부하 측정은 승인된 구현 단계에서 정한다.
- Windows 세션 보관·복원은 P-08·F11-03에서 설계한다.
- F05의 승인 단계·마감 취소 절차·정정 가능 기간 등 업무 흐름은 담당 문서에서 설계한다. 역할별 권한을 정한 것이 해당 기능 구현 완료를 뜻하지 않는다.

상세 의사결정은 [미정 사항 목록](../ROADMAP.md)을 함께 갱신한다. 새로운 기능이나 계약이 확정되면 이 문서를 수정하고 [인덱스](../README.md)의 범위·참조 경로도 갱신한다.
