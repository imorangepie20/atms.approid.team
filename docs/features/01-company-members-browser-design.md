## 제안 범위와 결정안

1. 기존 `/companies`에서 사용자가 선택한 회사 아래에 구성원 관리 영역을 둔다. 별도 전역 선택값을 만들지 않고 현재 화면의 명시적 회사 선택을 그대로 사용한다.
2. `company.members.manage` 권한이 있을 때만 `GET /api/companies/:companyId/members`를 호출하고 관리 UI를 표시한다. 권한이 없으면 구성원 정보를 요청하지 않고 “회사 관리자만 관리할 수 있음”을 안내한다.
3. 구성원 목록은 이메일·이메일 확인/계정 중지·회사 소속 활성 상태·다섯 역할·소속 version을 표시한다. UUID 오름차순 cursor와 25개 단위 “더 보기”를 사용하며 중지 소속도 이력으로 표시한다.
4. 활성·이메일 확인·전역 사용 가능 구성원만 역할을 수정한다. 다섯 역할 체크박스 중 1개 이상을 전체 집합으로 제출하고 순서만 다른 같은 집합은 저장하지 않는다.
5. 역할 변경과 소속 중지는 현재 비밀번호 재확인을 먼저 수행한다. 비밀번호는 제출 직후 화면 상태에서 지우고 저장·로그·오류에 남기지 않는다. 소속 중지는 대상 이메일과 “이 회사 접근이 중지됨”을 표시한 확인 단계 후 실행한다.
6. 본인 역할 변경 응답에 교체 세션이 있으면 기존 `adoptSession`으로 새 CSRF를 반영한다. 본인 소속 중지로 `sessionRevoked=true`이면 인증 상태와 캐시를 지우고 로그인 화면으로 이동한다. 다른 구성원의 변경은 현재 관리자 세션을 유지한다.
7. 오래된 소속 version·마지막 관리자 보호·경합의 409는 구성원 목록/상세를 다시 읽어 최신 역할·상태·version으로 교체하고 재시도를 안내한다. 400·401·403·404·409·503을 공통 오류 계약에 맞게 구분한다.
8. 관리자 초대·취소·재발송, 초대 수락, 세무사 접근 요청·취소·승인·반려, 중지 소속 재활성화, 본인 승인 설정은 이번 묶음에서 구현하지 않는다. 초대·접근 요청은 다음 브라우저 묶음, 본인 승인 설정은 그 뒤 설정 묶음으로 연결한다.

## 실제 실행 검증 기록

첫 브라우저 검증은 26개 중 18개 통과·8개 실패였다. 회사 등록/구성원 작업 비밀번호 label과 `회사 관리자` 안내 문구의 접근 가능한 이름 중복이 가장 앞선 공통 원인이어서 완료 게이트에 따라 수리를 멈추고 보고했다. 사용자 “오케이” 후 이름을 작업별로 분리하고 전체 묶음을 다시 실행했다. 두 번째 실행은 24/26 통과였고 역할 집합 요청 순서와 작업 결과 status 이름의 공통 원인을 수정했다. 세 번째 자동 검증은 26/26 통과했다.

첫 실제 DB 실행은 시험 사용자의 `password_hash` 누락으로 `users_active_password` 제약에서 중단됐고 제품 API는 실행되지 않았다. 실제 사용자 계약과 같은 Argon2id 해시를 쓰도록 fixture를 고친 뒤 전체 묶음을 다시 실행했다. 최종 build·lint exit 0, Appearance 16/16, 브라우저 26/26, 서버 19개 파일·413/413, 실제 DB 흐름이 모두 PASS다. lint의 기존 `UiIcons.tsx` 미사용 억제 주석 경고와 Vite 500kB 번들 경고는 종료 코드 0의 비차단 경고다.

실제 격리 DB에서는 실행 전용 구성원의 역할을 `READ_ONLY`에서 `ACCOUNTANT + READ_ONLY`로 바꾸고 소속을 중지해 version 1→3, active=false, 역할 변경/중지 감사 각 1건과 관리자 세션 유지를 확인했다.
