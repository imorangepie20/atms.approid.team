## 공통 Sidebar 서브메뉴 밀도 수리 확정 — 2026-10-07

사용자가 첨부한 운영 화면에서 `회계·세무` 아래 서브메뉴가 지나치게 떨어져 보이는 현상을 확인했다. 현재 각 링크는 `min-h-11`과 `py-3`, 목록은 `space-y-1`, 부모와 목록은 `mt-1`이어서 항목 중심 간격이 48 CSS px이고 첨부 화면 배율에서는 약 72px로 표현됐다.

사용자가 구체 조정안을 듣고 “수정해”라고 확정했다. 모바일에서는 44px 조작 영역을 유지하고, `md` 이상에서 서브메뉴를 36px(`min-h-9`, `py-2`)로 줄인다. 항목 간격과 부모-첫 항목 간격은 2px(`space-y-0.5`, `mt-0.5`)로 줄이며 활성 상태·색상·들여쓰기·포커스·경로는 유지한다. 구현 파일은 `src/components/layout/Sidebar.tsx`, `tests/e2e/appearance.spec.ts`이고, 완료 기록은 이 문서와 `docs/IMPLEMENTATION_PLAN.md`에 남긴다. 검증 조건은 375px에서 44px 이상, 1440px에서 36px 높이와 38px 중심 간격, 메뉴 경로·키보드 포커스·활성 상태 보존, DOM/Appearance/build/lint 통과다.

로컬 구현·검증 완료(2026-10-07): `mt-0.5`·`space-y-0.5`와 `md:min-h-9 md:py-2`를 적용했다. Playwright가 1440px에서 링크 높이 36px·중심 간격 38px, 375px에서 높이 44px 이상과 6개 경로를 확인했고 관련 13/13, Appearance16/16, DOM176/176, build/lint 종료0이다. 운영 실화면은 배포 뒤 확인한다.

## 확정한 금액 정책

**P-10 확정일: 2026-10-05.** 사용자 근거: 원화·소수 자릿수·Decimal/NUMERIC·반올림·계정과목·기초 잔액의 추천안을 제시한 뒤 “추천으로 하고 다음”으로 선택했다. 아래 값은 사용자가 선택한 프로젝트 정책이다. 라이브러리의 기본값이나 모든 세무 계산에 적용되는 법정 규칙으로 해석하지 않는다. 계정과목·기초 잔액의 담당 문서는 [확정한 계정과목과 기초 잔액](04-journals-ledger.md#확정한-계정과목과-기초-잔액)이다.

| 항목 | 확정한 정책 |
| --- | --- |
| MONEY-01 통화 | 첫 버전의 장부 통화는 원화(KRW) 하나이다. API와 업무 데이터에서 통화 식별을 유지하며 외화 장부·환율 환산·환산손익 자동 계산은 첫 범위에 포함하지 않는다. 원화 자료에 외화 금액을 그대로 더하지 않는다. |
| MONEY-02 입력·계산 자릿수 | 확정하는 전표 금액은 원 단위 정수이며 단가·수량 입력은 소수 6자리까지이다. 계산 중에는 Decimal을 사용하고 중간 단계마다 임의로 원 단위로 반올림하지 않는다. 입력의 허용 자릿수 초과는 오류로 안내하며 DB가 조용히 반올림하도록 맡기지 않는다. |
| MONEY-03 저장·범위 | DB의 공통 금액 저장 타입은 NUMERIC(24,6)으로 정한다. 총 유효 자릿수 24, 소수 자릿수 6이므로 정수부는 최대 18자리이다. 전표의 원 단위 제한은 별도 입력·업무 검증으로 지킨다. 저장할 값의 자릿수·범위를 사전에 검사하고 범위 초과·NaN·Infinity를 거부한다. 합계가 저장 범위를 넘는 경우에도 잘라 저장하지 않고 오류로 처리한다. F08-12에서 공통 저장 검사를 구현했다. 실제 전표 금액 필드·제약은 F04 단계에서 추가한다. |
| MONEY-04 API·화면 전달 | API 금액은 숫자형이 아닌 10진수 문자열로 전달하고 서버·클라이언트의 금액 계산은 Decimal 계약을 따른다. JavaScript Number의 이진 부동소수점 계산을 장부 금액 계산·대사에 사용하지 않는다. 원 단위 전표 금액의 예시는 "1234"이다. 천 단위 구분 기호는 화면 표시에서만 적용하며 원본 값과 통화를 보존한다. |
| MONEY-05 반올림 시점·예외 | 일반 계산은 필요한 최종 금액을 원 단위로 확정할 때 HALF_UP을 적용한다. 예: 123.5 → 124, -123.5 → -124. 산출값과 확정할 금액을 확인한 뒤 저장하며 입력·저장 단계에서 몰래 변경하지 않는다. 세무 계산은 세목·항목·기간별 법령의 절사·반올림 단위·시점·합산 순서가 우선한다. 해당 규칙이 없거나 검토되지 않았으면 일반 반올림으로 대체하지 않고 검토 대상으로 처리한다. 차변·대변 불일치를 반올림 차액으로 자동 보정하지 않는다. |
| MONEY-06 공통 설정·재현 | 통화·허용 자릿수·일반 반올림 등 공통 기본값은 기존에 확정한 하나의 공통 설정 파일에서 관리한다. 세무별 예외는 승인된 규칙 버전, 회사별 계정과목·기초 잔액은 업무 데이터로 보존한다. 표시 단위 변경은 원본 장부를 수정하지 않으며 확정 보고서의 입력·규칙·표시 조건과 버전을 함께 남긴다. F08-12 공통 계산·설정·입력·저장 검사는 구현됐다. 실제 업무 저장·API 적용과 확정 보고서 재현은 관련 기능에서 연결한다. |

공식 기술 근거: [PostgreSQL NUMERIC 문서](https://www.postgresql.org/docs/current/datatype-numeric.html)는 정확성이 필요한 금액 저장, precision/scale 및 초과 소수의 자동 반올림 동작을 설명한다. [Prisma Decimal 문서](https://www.prisma.io/docs/orm/v7/prisma-client/special-fields-and-types)는 Decimal.js 기반의 계산을 지원한다. [RFC 8259 제6절](https://www.rfc-editor.org/rfc/rfc8259.html#section-6)은 JSON 숫자의 구현별 범위·정밀도와 상호운용 한계를 설명한다. 이 근거를 바탕으로 문자열 전달을 선택했으며 NUMERIC(24,6), 원화 단일 장부와 HALF_UP은 프로젝트 선택이다. 기술 문서 확인만으로 세법별 반올림의 적법성을 검증한 것은 아니다.

영향 작업: F04-01·02·04·10, F06-04·08, F07-09·12·14, F08-10~12, F09-07, F13-03·09. [확정 기록](../PROJECT_DECISIONS.md#사전-결정-확정-기록)을 함께 참조한다. 공통 금액 계산·입력 계약·저장 검사는 F08-12에서, 기반 관계·기간 제약은 F08-11에서 구현했다. 실제 장부 API·전표 저장·세무 규칙 실행은 후속 기능이다.

## F08-10 API 공통 구현 계약

상태: **F08-10 구현·검증 완료**. 확정일: 2026-10-05. `code · message · details` 추천 형식과 RFC 9457 대안을 제시한 뒤 사용자가 “확정”으로 추천 형식을 선택했다. P-01·02·03·04·10의 선행 결정도 기록됐다. 아래 범위의 F08-10을 구현하고 전체 검증 묶음의 통과를 확인했다. 업무 API·금액 계산은 후속 항목이다.

### 변경 범위와 실행 흐름

1. `main.ts`에서 공통 설정 파일을 읽고 서버를 생성한다. PORT 기본값 4300, HOST 기본값 127.0.0.1, `/api` 경로와 정상 헬스 응답을 유지한다.
2. 공통 초기화 함수에서 Helmet, 입력 검증 파이프와 오류 필터를 등록한다. 파이프는 컨트롤러 실행 전에 입력 계약을 확인하는 NestJS 구성요소이고, 필터는 발생한 예외를 HTTP 오류 응답으로 바꾸는 구성요소이다.
3. 요청 본문·쿼리·경로에 선언한 Zod 스키마로 검증한다. 스키마는 필드·자료형·범위를 정의하며 NestJS 12의 내장 `StandardSchemaValidationPipe`로 실행한다. 후속 API는 `@Body({ schema })`, `@Query({ schema })`, `@Param({ schema })`에 `z.strictObject` 스키마를 명시한다. 스키마가 없는 입력은 파이프가 검증하지 않는다. 문자열 금액을 숫자로 자동 변환하지 않는다. 검증 실패 시 컨트롤러 메서드는 실행하지 않는다.
4. 모든 요청 오류는 아래 공통 응답으로 처리한다. 검증 실패·잘못된 JSON·없는 경로·DB 준비 실패·예상하지 못한 오류를 묶어 확인한다. 회사·인증·장부 API와 금액 계산은 각 후속 작업에서 구현한다.

### 확정한 응답 계약

성공 응답은 해당 기능의 기존 데이터 구조를 유지한다. 오류는 HTTP 상태와 함께 `code`, `message`, `details`를 전달한다. `details`는 입력 검증 오류의 필드·메시지 목록이며 다른 오류는 빈 배열이다. 아래는 형식 예시이며 실제 업무 API가 아니다.

```json
{
  "code": "VALIDATION_ERROR",
  "message": "입력값을 확인해 주세요.",
  "details": [{ "field": "name", "message": "값의 형식이나 범위를 확인해 주세요." }]
}
```

| 상황 | HTTP 상태 | 확정 오류 코드와 응답 원칙 |
| --- | --- | --- |
| 스키마 검증 실패 | 400 | VALIDATION_ERROR, 안전한 필드별 안내만 제공 |
| 잘못된 JSON·일반 잘못된 요청 | 400 | BAD_REQUEST, 원본 본문과 파서 예외를 노출하지 않음 |
| 없는 경로 | 404 | NOT_FOUND, 쿼리 문자열·토큰을 메시지에 복사하지 않음 |
| DB 준비 실패 | 503 | SERVICE_UNAVAILABLE, 연결 문자열·드라이버 오류를 노출하지 않음 |
| 예상하지 못한 요청 오류 | 500 | INTERNAL_ERROR, 고정 안내만 제공하고 스택·입력·내부 오류 내용을 전달하지 않음 |
| 기타 HTTP 오류 | 해당 상태 | 상태별 공통 코드·안전한 안내를 사용하고 내부 예외 메시지를 그대로 전달하지 않음 |

준비 실패의 HTTP 상태는 현재처럼 503이고 오류 본문은 확정한 공통 계약으로 바뀐다. 요청 식별·감사 이력은 F08-13에서 연결한다. 검증 라이브러리의 원문 메시지에는 입력값이 포함될 수 있으므로 필드별 메시지도 고정 안내를 사용한다. 후속 업무 스키마는 정적으로 선언한 객체 필드만 허용하고 미정의 필드를 거부한다.

### 코드를 읽는 순서

1. [main.ts](../../server/src/main.ts): `readAppConfig` → `NestFactory.create` → `configureApp` → 종료 훅 → `listen`. 기동 실패 catch는 HTTP 오류 필터와 별개다.
2. [app.config.ts](../../server/src/config/app.config.ts): API 기본값과 환경 변수 검증, 금액 정책 `MONEY_CONFIG`를 한 곳에서 관리한다. 로그인 1시간·최대 8시간 등 확정한 AUTH_POLICY와 Origin/쿠키 검사를 첫 인증 서버 묶음에서 추가했다.
3. [configure-app.ts](../../server/src/configure-app.ts): 운영과 테스트에서 같은 보안 헤더·경로·파이프·필터를 등록한다. `/api/` 아래의 리소스만 제공한다. prefix 밖과 빈 `/api`, `/api/` 경로도 전역 오류 계층으로 넘겨 고정 JSON 404를 반환한다. API 루트 엔드포인트를 추가할 때는 이 경로 계약도 갱신한다.
4. [api-validation.ts](../../server/src/common/api-validation.ts): 내장 파이프를 구성하며 검증 실패를 안전한 `ApiValidationException`으로 바꾼다. 필드 메시지는 고정 안내이고 객체 전체 오류의 필드는 `input`이다. 스키마 경로는 정적 필드명을 전제로 한다. 동적 키에 사용자 입력을 넣는 스키마는 이 계약의 대상이 아니다.
5. [api-exception.filter.ts](../../server/src/common/api-exception.filter.ts): 오류의 HTTP 상태를 보존하고 고정 안내를 전송한다. 검증 이외 오류의 details는 빈 배열이다. 500 이상 로그에도 원본 예외를 기록하지 않는다.
6. [AppModule](../../server/src/app.module.ts) → [HealthModule](../../server/src/health.module.ts): 기존 헬스 컨트롤러와 Prisma 서비스의 DB 초기화·종료 훅을 연결한다. 업무 모듈은 후속 구현이다.

검증 실행 순서: 로컬 PostgreSQL 기동 후 `cd server`에서 `npm.cmd test`. Prisma 클라이언트 생성과 TypeScript 빌드가 성공한 뒤 전체 테스트를 실행한다. F08-10 HTTP 테스트의 DB는 대역이며 F08-11 DB 테스트는 별도 실제 로컬 PostgreSQL DB를 사용한다. 홈서버 배포 상태는 검증하지 않는다.

의존성 참고: Zod 설치 후 `npm audit`는 기존 Prisma 개발 도구 의존성 경로의 high 4건(`prisma`, `@prisma/config`, `deepmerge-ts`, `mysql2`)을 보고했다. Zod 경로 경고는 없다. 자동 수정 제안은 Prisma 6.19.3으로의 주요 버전 변경이므로 이 작업에서 실행하지 않았다. 환경 의존성 정비 시 별도 검토한다.

### F08-10 검증 조건과 실행 결과

- 유효 입력만 업무 처리에 도달하고 필수값·타입·미정의 필드·본문/쿼리/경로 오류를 400으로 거부한다.
- 잘못된 JSON, 404, 503, 500의 공통 오류 형식·HTTP 상태와 민감정보 미노출을 실제 HTTP에서 확인한다.
- 기존 헬스 성공 응답·DB 장애 시 503, 환경 변수의 포트 검증과 설정값 재사용을 확인한다.
- 같은 작업 묶음에서 서버 테스트 전체·TypeScript 검사·서버 빌드를 실행하며 실패 수정 후 전체 묶음을 재실행한다.

2026-10-05 실행 결과: `npm.cmd run build`(Prisma generate + TypeScript), 전체 Vitest 테스트 모두 종료 코드 0. API 계약 44개와 기존 헬스 3개로 총 47개 PASS, 그중 민감정보 미노출 검증 14개 PASS. [실제 HTTP·설정 테스트](../../server/tests/api-contract.test.ts), [테스트 결과](../../.artifacts/implementation-f08-10-api-contract/tests.json), [5개 검증 묶음](../../.artifacts/implementation-f08-10-api-contract/preflight-results.json), [완료 체크와 근거](../IMPLEMENTATION_PLAN.md)를 참조한다. HTTP 테스트의 DB는 대역이며 실제 DB·홈서버 배포 상태와 원격 Hindsight 최신 문서 일치는 검증 범위 밖이다. Hindsight의 30분 예약만 현재 상태로 확인했다.

기술 근거: [NestJS 모듈](https://docs.nestjs.com/modules), [Pipes](https://docs.nestjs.com/pipes), [Exception filters](https://docs.nestjs.com/exception-filters). 설치된 `server/node_modules/@nestjs/common/pipes/standard-schema-validation.pipe.d.ts`에서도 해당 내장 파이프와 `exceptionFactory` 지원을 확인했다. 이 확인은 설계 근거이며 ATMS 입력 검증·오류 처리의 실행 검증 결과는 아니다.

## 기존 결정과 상세 요구사항

### 다음 F01·F08-13 서버 묶음 제안

[인증·세션·권한·감사 서버 설계](01-auth-session-design.md)에 첫 묶음의 범위·API·저장·설정·수정/생성 파일·검증 조건을 정리했다. 최초 수정 예정 파일은 기존 `server/src/config/app.config.ts`이며 정책값을 재확인하지 않고 기존 확정값을 사용한다. 사용자 “OK”로 첫 서버 범위를 확정해 로그인·세션·회사/역할 guard·DB 로그인 제한·감사 원자성을 구현했다. 실제 DB/HTTP를 포함한 전체 테스트 144개와 타입·빌드·컨테이너 검사가 통과했다. 첫 서버 부분의 완료이며 F01 또는 F08-13 전체 체크는 변경하지 않는다.

### 확정한 웹 세션 기반

P-02의 웹 로그인은 서버 세션 방식 + PostgreSQL 저장소로 확정했다. 브라우저는 HttpOnly·Secure·SameSite 쿠키로 세션 식별자를 전달하고 API마다 세션과 현재 회사·역할 권한을 확인한다. 상세 정책과 미정 사항은 [회사·사용자 권한의 웹 세션 방식](01-company-access.md#확정한-웹-세션-방식)을 따른다.

F08-11에서 세션 저장 모델과 해시·시간 순서 제약을 구현했다. 첫 서버 묶음에서 실제 세션 생성·쿠키·인증과 요청별 회사/역할 검사를 연결하고 검증했다. 가입·이메일·회사 관리·웹 화면은 후속 묶음이다. 로그인은 마지막 활동 후 1시간(60분) 미사용 시 만료하며 활동할 때마다 연장한다. 최대 유지 8시간과 활동 판정·쿠키·CSRF·가입·복구 정책은 [사용자 위임으로 확정한 인증 기본 정책](01-company-access.md#사용자-위임으로-확정한-인증-기본-정책)을 따른다. 라이브러리와 상세 API 계약은 해당 구현 단계에서 설계한다. [로그인 시간값과 설정 관리](01-company-access.md#확정한-로그인-시간값과-설정-관리)를 참조한다.

여러 기기 동시 로그인과 세션별 1시간(60분) 미사용 만료, 현재 세션·모든 기기 로그아웃을 제공하기로 확정했다. 서버 세션 무효화와 만료 범위는 [동시 로그인과 로그아웃 정책](01-company-access.md#확정한-동시-로그인과-로그아웃)을 따른다. 해당 기능은 구현 전이다.

서버 권한 검사는 같은 회사의 역할이 허용하는 권한을 합산하고 공통 제한을 우선 적용한다. 어느 역할에서도 허용하지 않은 작업은 거부한다. 상세 기준은 [권한 합산과 공통 제한](01-company-access.md#확정한-권한-합산과-공통-제한)을 따른다. F01-05~08 및 F08-13에서 적용하며 권한 검사 기능은 구현 전이다.

### 확정한 설정값 관리 원칙

사용자 확정일: 2026-10-05. 근거: “로그인 유지만료 시간 같은 설정값은 설정파일 하나에 모아서 처리하도록하자. 한시간으로해”.

- 로그인 유지·만료 시간 등 변경 가능한 설정값은 하나의 공통 설정 파일에 모아 관리한다.
- 각 기능은 해당 파일에서 읽은 값을 사용한다. 같은 정책값을 여러 파일에 하드코딩하거나 별도 기본값으로 중복 정의하지 않는다.
- 설정값의 의미와 단위를 명시하고, 서버 시작 시 필요한 값의 유효성을 확인하도록 설계한다. 시간값은 한 곳에서 정의하고 사용하는 API의 단위 변환도 공통 처리한다.
- 로그인 미사용 만료는 1시간(60분)이며 마지막 활동 기준으로 연장한다. 최대 유지 시간·링크 만료·요청 제한·해시 비용 등 기본값은 [인증 기본 정책](01-company-access.md#사용자-위임으로-확정한-인증-기본-정책)을 따르고 이 설정 파일에서 함께 관리한다.

공통 설정 파일은 F08-10에서 만든 `server/src/config/app.config.ts`이며 F08-12의 금액 설정을 추가했다. 인증 시간 설정과 첫 서버 세션·쿠키 사용은 F01·F08-13 첫 묶음에서 연결했다. 필수 결정 게이트와 확정한 구현 순서를 유지한다.

### Settings → Appearance 구현 계약

진입 경로: `/settings`에서 Appearance 선택 또는 `/settings?section=appearance`. 설정 메뉴 선택은 URL에 반영되며 브라우저 뒤로 가기로 복원된다.

| 설정 | 지원 값 | 기본값 | 적용 범위 |
| --- | --- | --- | --- |
| Theme | Light / Dark / System | Dark | 전체 화면 및 브라우저 기본 컨트롤 |
| Accent Color | Cyan / Indigo / Pink / Orange / Emerald / Red | Cyan | 공통 강조색, 버튼, 메뉴, 테두리, 그림자와 다크 배경 격자 |
| Font Size | Small 87.5% / Medium 100% / Large 112.5% | Medium | 브라우저 기본 글자 크기에 대한 rem 배율, Pretendard 유지 |

- 선택 즉시 적용하고 `localStorage`의 `atms.appearance.v1`에 자동 저장한다. Appearance에서는 Save Changes 버튼을 표시하지 않는다.
- 기기·브라우저별 표시 설정이며 서버 계정 저장과 다른 기기 동기화는 아직 구현하지 않았다.
- 기존 `theme` 키의 Light/Dark 선택은 새 설정이 없을 때 가져온다. 잘못된 필드는 개별 기본값으로 복구한다. 잘못된 JSON은 기존 테마 또는 기본값으로 복구한다.
- System은 OS 테마 변경을 따라간다. 상단 테마 버튼은 현재 표시 테마의 반대인 명시적 Light/Dark로 전환하며 나머지 설정을 유지한다.
- 저장소 사용이 금지되면 현재 화면에는 적용하고 새로고침 후 유지할 수 없음을 안내한다.
- Reset to defaults는 세 설정을 즉시 기본값으로 복원하고 저장한다. 미리보기 금액은 예시이며 실제 회계 데이터가 아니다.
- 네이티브 라디오 그룹과 선택 체크 표시를 사용한다. Tab/방향키 조작, 포커스 표시, 좁은 화면 탐색 메뉴 및 기기의 동작 줄이기 설정을 지원한다.

구현 파일: [설정 화면](../../src/pages/Settings.tsx), [Appearance 컴포넌트](../../src/components/settings/AppearanceSettings.tsx), [공통 테마 상태](../../src/context/ThemeContext.tsx), [저장 계약과 팔레트](../../src/context/appearance.ts), [스타일](../../src/index.css).

검증 명령: `npm.cmd run test:appearance`, `npm.cmd run build`. 저장값 복구와 6개 팔레트의 양 테마 텍스트 대비 검증은 [회귀 테스트](../../tests/appearance.test.cjs)에서 실행한다. 브라우저 검증은 테마·색상·크기 전체 적용, 재접속 복원, System 변경, 상단 버튼, 기본값 복원, 저장 실패 안내, 키보드와 모바일 화면을 대상으로 한다.

아래 내용은 종합 문서에서 옮긴 결정 및 요구사항이다. 기술 버전과 적용·검증 기록의 기준일은 2026년 10월 5일이며, 이번 문서 분리 작업에서 기능이나 외부 서비스 상태를 재검증한 결과는 아니다.

### 회계 데이터 설계 권장 기준

이 절은 구현 전 설계 기준이다. 금액 정책은 위 P-10을 적용하고 실제 세무 규정과 신고 양식은 [P-04 범위](06-tax.md#사용자-위임으로-확정한-첫-세무-범위)의 대상 국가·신고 종류·적용 기간에 맞추어 검증한다.

1. **금액 정확성**: 서버 계산에 Decimal, 데이터베이스에 NUMERIC을 사용하고 API의 금액은 문자열로 전달한다. 통화별 소수 자릿수와 반올림 시점을 명시한다. PostgreSQL은 정확한 계산이 필요한 금액에 NUMERIC을 권장하며, Prisma는 Decimal 타입을 제공한다. [PostgreSQL 숫자 타입](https://www.postgresql.org/docs/current/datatype-numeric.html), [Prisma Decimal 문서](https://www.prisma.io/docs/orm/v7/prisma-client/special-fields-and-types)
2. **전표 원자성**: 전표와 분개를 하나의 트랜잭션으로 저장하고 차변 및 대변 합계 일치를 검증한다.
3. **중복과 충돌 처리**: 중복 제출을 방지할 식별자와 동시에 수정할 때의 충돌 처리 방식을 둔다.
4. **확정 후 정정**: 확정 전표는 원본을 남기고 역분개나 연결된 정정 전표로 수정 이력을 기록한다.
5. **승인과 마감**: 작성, 승인, 확정, 마감 상태와 상태별 권한을 정의한다.
6. **회사별 접근 제한**: 모든 조회와 변경에서 소속 회사 및 권한을 검증한다. 여러 회사를 지원할 경우 데이터베이스의 행 수준 보안도 검토한다.
7. **재현 가능한 세무 집계**: 적용 연도, 세율 및 계산 규칙 버전을 기록하여 과거 결과를 재현한다.
8. **복구 검증**: 백업뿐 아니라 실제 복원과 특정 시점 복구 절차를 검증한다.

[다섯 번째 초대·접근 요청 서버 제안](01-company-invitations-design.md)은 기존 Auth/DB/메일/세션 기반을 공유하고 14개 파일과 새 모델 2개/추가 SQL을 제안한다. 승인 후 중앙 설정을 첫 파일로 다루며 목표 모델 15개/마이그레이션 7개는 아직 적용 상태가 아니다. 여덟 선택은 사용자 확정 대기, API 11개·미실행 조건 8개를 구분한다. 코드·환경·패키지와 상위 완료 체크를 변경하지 않는다.

재개 최신 상태(2026-10-05): [중첩 입력 수정·테스트 초기화 실패·수리 중단](01-company-invitations-design.md#재개-검증-실패와-공통-테스트-초기화-원인). 승인한 2개 파일 수정 후 build/runtime은 통과했다. 전체 347개 중 314개 통과·33개 공통 초기화 실패로 완료되지 않았다. 기본 DB 13개 테이블·6개 마이그레이션과 기존 환경을 유지한다.

다섯 번째 F01 서버 부분 완료(2026-10-05): [초대·접근 요청 실행 기록](01-company-invitations-design.md#실제-실행-검증-기록)의 전체 347개 테스트·8개 조건 PASS. schema/build/DB 타입·컨테이너·로컬 추가 마이그레이션 각 exit 0이며 로컬 업무 테이블 15개·마이그레이션 7개다. 이전 실패 상태와 별도로 기록하며 기존 자료/환경·정책과 전체 F01/F08-13 체크를 보존한다.

여섯 번째 F01·F08-13 설정 서버 묶음 완료(2026-10-05): 사용자가 [회사 본인 승인 설정 설계](01-company-settings-design.md)를 지정한 “OK”로 여섯 선택·9개 파일을 확정했다. 기존 공통 설정/권한/세션을 재사용해 현재 회사 설정·공유 version·엄격한 입력·원자 감사를 구현했다. 감사 사건의 DB CHECK만 여덟 번째 SQL로 확장하여 기존 27개와 새 사건 1개를 허용한다. 모델/테이블은 15개를 유지하고 기존 자료·환경을 보존했으며 seed는 실행하지 않았다. 전체 391개 테스트·8개 조건과 schema/타입/build/컨테이너/구 자료 업그레이드가 PASS다. 실제 승인 API·웹 화면과 상위 기능 체크는 후속이다.
